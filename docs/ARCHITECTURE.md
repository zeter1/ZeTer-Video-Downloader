# ARCHITECTURE

## Структура

```text
video_downloader.py       # запуск
src/
  application.py          # композиция mixin + короткая оркестрация старта
  bootstrap.py            # main/crash startup
  app/                    # пути и mutable-state инициализации
  core/                   # общие runtime-механизмы
  downloads/              # URL, yt-dlp, 1080p, очередь, media validation
  audio/                  # convert / merge / split
  ui/                     # Tkinter UI по зонам ответственности
  diagnostics/            # problem logs, retention, schema, incidents, validator
docs/                     # документация
Настройки/                 # пользовательские настройки
```

## Как искать нужный код

1. UI-проблема → `src/ui/`.
2. Не скачивает / плохое качество / yt-dlp → `src/downloads/`; workflow — `youtube_downloader.py`, каталог fallback — `youtube_strategy_catalog.py`, CLI args — `youtube_command.py`.
3. subprocess зависает / отмена → `src/core/subprocess_runner.py`, `process_control.py`, `ytdlp_runtime.py`.
4. Конвертация/склейка/разрезание аудио → `src/audio/`.
5. Логи проблем → `src/diagnostics/`.
6. Настройки → `src/core/settings.py`; пути/папки → `src/app/paths.py`; runtime-state → `src/app/state.py`.

## 1080p contract

- Программа не должна выбирать видео выше 1080p.
- В основном и резервном high-quality селекторах готовое видео со звуком участвует в выборе наравне с раздельными потоками; наличие отдельных дорожек не исключает готовое 1080p.
- Если 1080p доступно, high-quality video+audio стратегии должны получить приоритет перед progressive 720p/360p.
- Результат ниже 1080p от high-quality стратегии — резерв, а не немедленный успех. Исключение: широкий горизонтальный кадр шириной от 1920 и высотой больше 720 при соблюдении лимита 1080, например 1920×1032, считается достигнутым Full-HD-классом. Обычное 1280×720 и портретный кадр под это исключение не попадают.
- После исчерпания high-quality путей допустим лучший реально доступный вариант ниже 1080p.
- Фактическое разрешение определяется через ffprobe, а не по имени формата yt-dlp.

## Почему много небольших файлов

Разделение сделано по owner-логике: каждый файл отвечает за одну понятную область. Это позволяет ChatGPT/Codex сначала читать 1–3 релевантных файла вместо нескольких тысяч строк монолита.

Token-efficient границы отделяют orchestration от деталей: `youtube_downloader.py` держит control flow, `youtube_attempt.py` — setup/context, `youtube_retry.py` — классификацию ошибок, `youtube_success.py` — обработку успешного результата, `youtube_finalize.py` — финальный fallback/reporting, `youtube_strategy_catalog.py` — каталог стратегий, `youtube_command.py` — CLI. Инициализация путей/state вынесена из `application.py` в `src/app/`.
`youtube_queue_policy.py` владеет временными исключениями способов и бюджетом неудач; `youtube_candidate_formats.py` — исключением уже скачанных низких video-format ID в том же контексте выбора.
Большие diagnostic utility-модули также разделены: `validator.py` и `retention.py` оставлены короткими фасадами, а core/integrity/session и base/archive/storage детали вынесены в отдельные owner-файлы.

## Итоги очередей и целостность диагностики

Пути пользовательского состояния остаются рядом с `video_downloader.py` и определяются `app/paths.py`. Схема problem logs сохраняет обратную совместимость. `diagnostics/schema_manifest.py` генерирует `Логи проблем/README_FOR_CODEX.md`; существующие исторические сессии при изменении кода не переписываются.

`summary_writer.py` хранит `download_batches` с отдельными результатами очередей и `download_totals` с суммами за запуск. Повторная публикация одной очереди не удваивает суммы. `download_outcome` сохраняет неудачу ранней очереди даже после следующей успешной; `status` отдельно описывает жизненный цикл приложения. Поле `context` содержит последний результат, включая `failed`, и сведения о завершении. История здоровья и человеческая сводка используют общие итоги. Время начала диагностической сессии не заменяется временем последней очереди.

`reporting.py` последовательно выполняет выделение номера события, запись вложения и обеих JSONL-копий под одним `problem_record_write_lock`. Обычный `problem_log_lock` защищает счётчики и сводки. `lifecycle.py` проверяет terminal-state и публикует состояние под одним atomic-write lock: отложенный heartbeat не открывает завершённый запуск заново.

Намерение завершить запуск фиксируется до записи terminal-state; успешная публикация обоих state-файлов учитывается отдельно. Если корневой указатель не записался, повторная финализация может опубликовать его заново. Поздние события остаются в журнале и обновляют счётчики, сохраняя terminal-статус сводки и указателей.

`retention_storage.py` создаёт уникальные временные файлы рядом с целью, закрывает их перед заменой и отвергает невалидный JSON до записи. Повторяется только замена при Windows sharing/lock conflict 32/33 в существующем ограниченном бюджете. Отказ доступа 5 не считается автоматически временным: предыдущий корневой файл сохраняется, а отказ попадает в независимый emergency log. Между локальным state и корневым указателем нет многофайловой транзакции; при сбое следует читать оба файла и emergency log. Эти меры не устанавливают, какой внешний процесс вызвал исторический отказ доступа.

Автоматические проверки используют `VideoDownloader.__new__` и синтетические пути fixture, без запуска GUI и чтения пользовательских настроек. При проверках `TEMP/TMP` направляются в доступный тестовый каталог; конструктор приложения не вызывается. Живой YouTube, Windows GUI и EXE требуют отдельных проверок.


## Выбор качества и выполнение

- Подключение использует маршрут Windows/VPN и автоматический системный прокси yt-dlp. Без явного прокси приложения `--proxy` не передаётся; заданный прокси не обходится автоматически. `manager.py` запускает очередь без предварительного прямого TCP-теста YouTube/публичных DNS: он не учитывает системный прокси и не доказывает доступность выбранного сайта. Ошибка доступа к реальной ссылке обрабатывается обычной цепочкой yt-dlp/task/retry и сохраняет неудачный результат.
- Селектор ограничивает высоту 1080; сортировка начинается с высоты, затем учитывает язык для YouTube, контейнеры и битрейты. Предпочтение расширения не понижает разрешение. Основной профиль допускает только прямые HTTP(S)-потоки; HLS остаётся явным резервом. Итоговое видео публикуется в MP4 через `downloads/mp4_output.py` и `downloads/files.py`.
- При наличии русской аудиодорожки готовый поток с явно другим языком не подменяет её в предпочтительной ветке. При отсутствии подходящего языка доступны общие резервные ветки.
- Progressive остаётся резервом; недоступность форматов/сети может ограничить достигнутое качество. Битрейты разных кодеков не являются прямой мерой визуального качества.
- Временные исключения способов действуют только внутри очереди и сбрасываются перед новой. IPv6 DNS и чтение cookies Chrome исключаются по явной ошибке; iOS — после отсутствия форматов у трёх разных видео, раздельно по профилям. Общая сетевая ошибка и название файла не являются доказательством запроса авторизации.
- Перед следующей попыткой применяется бюджет из `core/constants.py`: 12 неудач либо 600 секунд суммарной работы завершившихся неудачных попыток. Валидный сохранённый резерв и успешная долгая загрузка бюджет не расходуют; текущую прогрессирующую попытку этот бюджет не обрывает. Существующие watchdog и абсолютный timeout действуют отдельно, а сообщения различают отсутствие вывода, отсутствие прогресса и общий предел времени.
- Повторно не скачивается доказанный низкий video-format ID в том же client/auth/EJS/profile контексте. Исключение не переносится на другой клиент или аудиодорожку; неразобранные DOWNLOAD_PLAN не используются как основание фильтрации. При исчерпании бюджета сохраняется лучший валидный кандидат, если он есть.
- Настройки фоновой сессии фиксируются на главном потоке перед запуском worker; изменения UI действуют со следующей сессии.
- Проверка MP3 отклоняет неизвестную длительность и отклонения в обе стороны от допуска из `src/core/constants.py`. Проверка длительности не доказывает идентичность содержимого.
- Проверки: `python -m unittest discover -s tests`; импорт `src.application` не запускает GUI. Конструктор приложения создаёт состояние относительно корня проекта, поэтому для проверок используйте изолированную копию без пользовательских данных.
- `tests/__init__.py` закрепляет локальное пространство имён `tests.support`, чтобы установленный сторонний пакет `tests` не подменял диагностические fixtures.
- Ручная проверка: скачать короткое видео с доступным 1080p, проверить разрешение и начало/конец MP3; затем отменить следующую загрузку и начать новую с изменёнными настройками.

При ошибке публикации `.preserve_download` защищает папку результата от очистки следующей сессией. Каждый запуск получает отдельную временную папку. Защищённые результаты сохраняются для ручного восстановления; автоматического срока удаления у них нет.

## Временные каталоги загрузки

`downloads/files.py::cleanup_empty_download_temp_roots` обслуживает только непосредственные дочерние каталоги `Видео/_temp_downloads` и `Видео/_quality_candidates`. `downloads/manager.py` вызывает его при завершении очереди после выхода из executor, когда workers остановлены, в том числе при ошибке и отмене. Удаление выполняется только через `rmdir`: непустые каталоги, файлы результатов и recovery-данные не затрагиваются. Проверяются canonical parent, тип, reparse-атрибуты и identity каталога перед удалением; ссылки и junction пропускаются. Отказ доступа записывается как предупреждение и не меняет результат скачивания.

Маркер `.preserve_download`, создаваемый перед нормализацией/публикацией готового файла, защищает единственную пригодную для восстановления копию. Общая failure-очистка yt-dlp сохраняет как job-каталог, так и резерв качества с этим маркером. Старый startup-cleanup имеет отдельного владельца `cleanup_stale_download_temp_dirs`; завершение очереди не вызывает его и не расширяет удаление старых данных.

## Текстовые сочетания

В поле URL используются штатные виртуальные текстовые события Tk. Windows Tk назначает NumLock флагу Mod1 (`0x8`), поэтому этот флаг разрешён обработчиком Ctrl; Alt проверяется через Mod2 (`0x10`) и `ALT_MASK` (`0x20000`). Владельцы: `ui/clipboard.py`, `ui/helpers.py`, регистрация в `ui/layout.py`.

## Завершение очереди

Менеджер считывает результаты фоновых задач. Необработанные ошибки привязываются к ссылке и попадают в список неудачных загрузок. Завершение вызывается через `finally`, в том числе после ошибки создания папки или конвертации. `download_outcome` различает `completed`, `failed`, `cancelled`; интерфейс различает отмену, неудачные загрузки и исключения, дошедшие до менеджера. Ошибки и отмена объединения/разбиения аудио передаются менеджеру. Повторный запуск во время активной сессии игнорируется.


## Уведомление о завершении и выбор папки

`src/ui/completion_notification.py` отвечает за постоянные окна поверх остальных в рабочей области основного экрана Windows, над панелью задач. Завершение всей очереди передаётся из `downloads/progress.py` через thread-safe очередь; единственный poller создаётся и отменяется главным потоком Tk. Закрытие root останавливает poller и отслеживание переменной пути, поздние завершения не создают окна.

`downloads/manager.py` блокирует поле `save_path_entry` и кнопку `browse_path_btn` перед запуском worker. `downloads/progress.py` разблокирует их только при обработке завершения, включая ошибку, отмену и отказ запуска потока. `ui/settings_controls.py` дополнительно отклоняет выбор папки во время активной задачи, в том числе результат диалога, если задача началась при открытом диалоге.

Уведомление не имеет таймера закрытия; открытие папки его не уничтожает. Повторные задачи создают отдельные окна. Текст пути обновляется через trace текущего `save_path`, кнопка читает тот же путь при нажатии. Ручная проверка: выбрать папку → начать короткую задачу → проверить блокировку на скачивании и конвертации → переключиться в другое окно → проверить уведомление справа внизу и открытие выбранной папки → изменить путь после завершения → проверить обновление уведомления → закрыть его крестиком. Отдельно проверить отмену и последующий запуск.

Автоматические проверки не открывают GUI: `tests/test_completion_notification.py` проверяет очередь, жизненный цикл, сохранение окна, путь и блокировку на узкой подмене Tk/Проводника. Это не подтверждает внешний вид, фокус и native поведение Windows.

## Безопасность аудиорезультатов

Конвертация не использует существующий MP3 только по совпадению имени и длительности: создаётся новый файл со свободным именем. Старые файлы сохраняются.

Объединение требует наличия всех указанных входов и конечных положительных длительностей. Merge и split выполняются в отдельных `.merge_*`/`.split_*` папках внутри «Разбивка аудио». При сбое рабочая папка сохраняется для ручного восстановления; автоматической очистки таких материалов нет. Split не удаляет исходник; merge удаляет свой промежуточный MP3 только после успешного сохранения частей.

Перед сохранением проверяются результат FFmpeg, наличие частей и расхождение общей длительности менее допуска из `src/core/constants.py`. Разбиение не создаёт границу в последние 0,1 секунды: короткий хвост остаётся в последней части. Старые итоги не перезаписываются. При отказе переноса частей выполняется возврат уже перенесённых частей в рабочую папку. Если файловая система блокирует и возврат, оставшийся путь явно записывается в диагностику; исходник сохраняется, операция не объявляется успешной.

Реальная локальная проверка использует разные звуковые тоны и проверяет их порядок после объединения/разбиения. Проверка длительности произвольного пользовательского материала не доказывает идентичность всех сэмплов. Ручной тест: два коротких видео → MP3 → объединение, затем отмена и повторный запуск; проверить, что прежние MP3 сохранены и итоговый статус соответствует результату.

## Архитектура обновления Windows EXE

**Границы ответственности:** `src/ui/update_controls.py` управляет настройкой фоновой проверки, worker-thread и подтверждениями через Tk; `src/core/app_updates.py` отвечает за идентичность сборки, GitHub Releases API, доверенный URL, SHA-256, staging и автономную замену EXE.

```text
EXE (PyInstaller) → build_info.json (repository, commit, build-<sha7>)
                       ↓
ui/update_controls.py → background check → GitHub Releases
                       ↓
core/app_updates.py → валидный build-* + verified digest
                       ↓
                 download .part → SHA-256 → staging
                       ↓
           согласие пользователя → завершение приложения
                       ↓
         apply-update.ps1 → backup → replace / restore
```

Инварианты безопасности и UX:

- Обновление предназначено **только для упакованной Windows-сборки** с корректным embedded `build_info.json`; запуск из Python и старые EXE без идентификатора требуют ручного обновления.
- `parse_releases` учитывает опубликованные Releases, включая **Prerelease**, сравнивает текущий тег среди распознанных, сортирует по времени публикации и отвергает ассеты без `sha256:<64 hex>` или с неожиданным URL. Не используйте `/releases/latest` как единственный источник.
- `download_verified` ограничивает общий объём, использует временный файл `.part` и проверяет хеш **до** staging; сбой не должен выглядеть как успешно установленное обновление.
- Проверка сети и скачивание выполняются на worker thread, сообщения выводятся через главный поток Tk; установка требует согласия и откладывается при активной загрузке.
- Отдельный PowerShell helper запускается после завершения приложения, проверяет checksum, создаёт резервную копию и пытается восстановить исходный EXE при ошибке. **Пользовательские настройки, историю, логи и медиа не удалять.**
- Для регрессий предусмотрен `tests/test_app_updates.py`; живую замену заблокированного EXE, права к файловой системе и Windows SmartScreen нужно проверять отдельно, offline-тесты их не подтверждают.
